# CLI 기반 Codex Pet 설치 흐름 구현계획

- 상태: 실행 대기
- 선행 계획: [CLI 설치 전환 문서화 실행계획](./documentation-update-plan.md)
- 목적: 생성한 Maple 캐릭터 Pet을 `.codex-pet.zip`으로 발행하고 `npx` CLI로 로컬 Codex Pet 디렉터리에 설치한다.
- 실행 제약: 이 계획을 수행할 때 서브에이전트를 생성하지 않고 단일 에이전트가 직접 작업한다.

## 1. 고정 아키텍처

- npm 패키지와 실행 바이너리 이름은 모두 `maple-hatch-pet`이며 설치 방식은 `npx maple-hatch-pet add <petId>` 하나다.
- `codex://pets/install`과 `codex://new?prompt=...`는 구현하지 않는다.
- 설치 모달에 ZIP 직접 다운로드 링크나 수동 설치 절차를 제공하지 않는다.
- 서버는 생성마다 UUID `petId`를 발급한다.
- 서버는 v1 `spritesheet.png`와 `pet.json`을 `.codex-pet.zip`으로 묶는다.
- 패키지는 Vercel Blob 공개 저장소에 고유하고 변경되지 않는 객체로 발행한다.
- CLI는 서비스의 다운로드 API에서 패키지를 받고 검증한 뒤 `<user-home>/.codex/pets/<petId>`에 설치한다.
- Supabase, 다른 데이터베이스, 사용자 계정, 보관함과 갤러리는 추가하지 않는다.
- CLI 코드는 저장소 최상위 `cli/`에 둔다.

## 2. 성공 기준

1. 유효한 캐릭터 생성 응답에 `petId`, `packageUrl`, `installCommand`, `expiresAt`이 포함된다.
2. 발행된 ZIP은 루트에 `pet.json`과 `spritesheet.png`만 포함하고 두 파일의 계약이 일치한다.
3. CLI의 `add <petId>`가 지원 플랫폼의 현재 사용자 Codex Pet 디렉터리에 패키지를 설치한다.
4. 같은 `petId`를 다시 설치하면 별도 확인이나 옵션 없이 검증된 새 패키지로 교체한다.
5. 실패한 다운로드나 검증은 부분 설치를 남기지 않고 기존 설치를 보존한다.
6. 생성 성공 모달에서 CLI 명령만 확인하고 복사할 수 있다.
7. 설치한 Pet은 ChatGPT 데스크톱 앱의 Pets 새로고침 후 선택 가능한 구조를 가진다.

## 3. 확정된 구현 결정

구현은 다음 값을 변경하지 않고 따른다.

- npm 패키지 이름: `maple-hatch-pet`
- CLI 바이너리 이름: `maple-hatch-pet`
- 동일 `petId` 재설치: `--force` 없이 항상 안전하게 교체
- 설치 UI: `npx maple-hatch-pet add <petId>`만 표시하고 ZIP 직접 다운로드는 제공하지 않음

결정되지 않은 기능이나 옵션을 편의를 이유로 추가하지 않는다.

## 4. 단계별 구현

### 1단계: 계약과 현재 구현의 변경 지점 고정

- 문서화 계획이 완료됐는지 확인한다.
- 현재 `buildPetDeepLink`, 생성 응답 타입, 설치 모달, Blob 발행과 Cron 정리의 호출 경계를 식별한다.
- 기존 미커밋 변경과 겹치는 파일을 확인하고 관련 없는 변경을 보존한다.

검증: 변경 대상 파일 목록과 새 계약 필드가 문서와 일치하는지만 확인한다.

### 2단계: Pet 패키지 생성

- 서버가 스프라이트 PNG 검증을 통과한 뒤 UUID `petId`를 생성하게 한다.
- `pet.json`을 CLI 계약의 스키마대로 직렬화한다.
- ZIP 루트에 `pet.json`과 `spritesheet.png`만 넣는다.
- ZIP 라이브러리는 서버 런타임에서 동작하는 최소 의존성 하나만 선택하고 lockfile에 고정한다.
- 패키지 생성 실패는 공개 발행 전에 현재 오류 envelope으로 종료한다.

검증: 정상 v1 패키지 한 건의 파일 목록과 manifest 일치, 잘못된 manifest 또는 ZIP 생성 실패 한 건을 대상으로 단위 테스트한다.

### 3단계: Vercel Blob 발행과 다운로드

- Blob 경로를 `pet-packages/<petId>.codex-pet.zip`처럼 `petId`로 식별 가능한 형태로 고정한다.
- 공개 HTTPS 다운로드와 올바른 콘텐츠 타입을 확인한 뒤에만 성공 응답을 만든다.
- CLI가 `petId`로 패키지를 받을 다운로드 Route Handler를 추가한다.
- 만료되거나 없는 ID는 `404`, 저장소 장애는 `503`으로 처리한다.
- Cron 정리 대상을 새 패키지 접두사에 맞춘다.
- DB나 별도 메타데이터 조회 테이블은 만들지 않는다.

검증: 발행 성공, 존재하지 않는 ID, 콘텐츠 타입 불일치와 만료 정리 경계만 단위 테스트한다.

### 4단계: 생성 API 응답 변경

- 기존 `spritesheetUrl`과 `deepLink`를 외부 성공 응답에서 제거한다.
- `petId`, `packageUrl`, `installCommand`, `expiresAt`을 반환한다.
- 서버가 `npx maple-hatch-pet add <petId>` 형식으로 설치 명령을 만들게 한다.
- 로그에 닉네임, 패키지 URL, 사용자 로컬 경로를 남기지 않는다.

검증: 성공 응답 한 건과 패키지 발행 실패 응답 한 건을 대상으로 API 단위 테스트를 갱신한다.

### 5단계: npm CLI 패키지

- 최상위 `cli/`에 npm 패키지와 실행 바이너리 이름이 모두 `maple-hatch-pet`인 독립 `package.json`, TypeScript 설정, 실행 진입점과 테스트를 둔다.
- `add <petId>`만 우선 구현하고 요청하지 않은 검색·목록·삭제 명령은 추가하지 않는다.
- `petId` 형식을 검증한 뒤 고정된 Production 서비스 origin에서만 다운로드한다.
- 다운로드 크기를 제한하고 ZIP 엔트리, `pet.json`, 스프라이트 형식·크기와 버전을 검증한다.
- 절대 경로, `..`, 드라이브 문자와 심볼릭 링크 엔트리를 거부한다.
- Node의 `os.homedir()`, `os.tmpdir()`와 `path`를 사용하고 운영체제 경로를 하드코딩하지 않는다.
- 임시 디렉터리에서 새 패키지 검증을 마친 뒤에만 최종 디렉터리에 반영한다.
- 같은 `petId`의 기존 설치가 있으면 별도 확인이나 `--force` 없이 검증된 새 설치로 교체한다.
- 교체 반영 중 실패하면 기존 설치를 복원하고 임시 산출물만 정리한다.
- 성공 메시지는 최초 설치와 재설치를 구분한다.
- `--force` 옵션은 구현하지 않는다.

검증: 경로 계산, 최초 설치, 동일 ID 재설치, 재설치 다운로드·검증 실패 시 기존 설치 보존, 잘못된 ID·ZIP과 경로 순회의 핵심 분기만 단위 테스트한다. 모든 ZIP 변형을 조합한 대규모 퍼징은 MVP 범위에 포함하지 않는다.

### 6단계: 설치 모달 변경

- 생성 결과 타입을 새 API 응답에 맞춘다.
- `Codex에 설치` 링크를 읽기 가능한 설치 명령과 `설치 명령 복사` 버튼으로 바꾼다.
- 설치 모달에는 ZIP 직접 다운로드 링크를 렌더링하지 않는다.
- 복사 성공은 짧은 접근 가능한 상태 문구로 알리고 중복 알림을 쌓지 않는다.
- 28일 만료와 터미널 실행, 설치 후 Pets 새로고침 안내를 표시한다.
- 모달 닫기·재열기, 포커스 트랩, 설정 변경 시 결과 무효화는 현재 계약을 유지한다.
- 딥링크 생성 유틸과 그 변경으로 사용되지 않는 코드·테스트만 제거한다.

검증: 명령 표시, 복사 성공, ZIP 링크 부재와 설정 변경 후 결과 제거를 컴포넌트 단위에서 확인한다. 화면 검증과 E2E는 사용자가 명시적으로 요청할 때만 실행한다.

### 7단계: 개인정보와 운영 표면 정렬

- `/privacy`의 공개 자산 설명을 PNG URL에서 Pet 패키지와 `petId`로 갱신한다.
- 삭제 요청 본문에 포함할 식별자를 새 계약과 맞춘다.
- 운영 로그와 대시보드 관찰 항목의 Blob 접두사를 새 패키지 경로에 맞춘다.
- 사용자 계정, 설치 이력과 다운로드 통계는 추가하지 않는다.

검증: 관련 문구와 객체 접두사가 현재 계약과 일치하는지 검색으로 확인한다.

### 8단계: npm 패키지 산출물 확인

- CLI 패키지의 `bin`, 배포 파일 allowlist와 Node 엔진을 확인한다.
- 실제 게시 직전에 npm 공개 레지스트리에서 `maple-hatch-pet` 이름의 사용 가능 여부를 다시 확인한다.
- 패키지에 테스트, 로컬 설정, 비밀값과 불필요한 저장소 파일이 포함되지 않게 한다.
- 실제 npm 게시와 Production 배포는 사용자의 별도 요청과 자격 증명 승인이 있을 때만 수행한다.

검증: 게시하지 않는 로컬 패키지 목록 확인까지만 기본 범위로 한다.

## 5. 검증 범위 제한

기본 검증은 변경 위험에 직접 대응하는 최소 범위로 제한한다.

- 변경한 서버·CLI·컴포넌트의 관련 단위 테스트만 실행한다.
- 타입 영향이 넓을 때만 관련 타입 검사를 한 번 실행한다.
- 문서와 코드의 계약 이름은 `rg` 한 번과 diff 검토로 확인한다.
- 동일 사실을 단위 테스트, E2E, 수동 실행과 화면 검증으로 반복 확인하지 않는다.
- `npm run check`, 전체 테스트, 빌드, E2E, 화면 검증, 실제 npm 게시와 Production smoke test는 사용자가 명시적으로 요청하지 않으면 실행하지 않는다.
- 보안상 필수인 ZIP 경로 순회, 용량 제한과 원자적 설치 검증은 생략하지 않되 가능한 입력 조합을 전부 열거하는 과도한 테스트는 만들지 않는다.

## 6. 범위 제외

- Supabase 또는 다른 DB
- 로그인, 사용자 계정과 생성 이력
- 갤러리, 검색, 추천과 설치 통계
- `codex://` 딥링크
- curl·PowerShell·수동 압축 해제를 공식 설치 수단으로 제공하는 기능
- CLI의 목록, 검색, 업데이트와 삭제 명령
- Codex sprite v2 생성

## 7. 최종 인계 내용

구현 완료 시 다음만 간단히 보고한다.

- 변경된 설치 흐름과 명령
- 생성 API와 패키지 계약의 변경점
- CLI가 설치하는 논리 경로
- 실행한 최소 검증과 실행하지 않은 빌드·화면 검증
- npm 게시 또는 Production 배포처럼 아직 사용자의 별도 승인이 필요한 작업
